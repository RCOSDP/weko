h2. 根本原因が判明したもの — グループ未設定のインデックスが誰にも見えない

*@weko_index_tree.utils.check_groups()@ が、グループを設定していない
インデックスで必ず @False@ を返す。*

<pre><code class="python">
def check_groups(user_group_list, index_group_list,
                 user_role_group, index_role_group):
    if current_user.is_authenticated and not user_group_list and not user_role_group:
        user_group_list.append('-89')
    elif not current_user.is_authenticated:
        user_group_list.append('-89')

    group_perm = any(r in user_group_list for r in index_group_list)
    role_group_perm = any(r in user_role_group for r in index_role_group)
    return group_perm or role_group_perm
</code></pre>

@index_group_list@ が空だと @any()@ は必ず @False@ になる。
@check_index_permission_by_role_and_group@ は

<pre><code class="python">
return check_roles(...) and check_groups(...)
</code></pre>

なので、ロール判定を通っても*グループ判定で必ず落ちる*。結果、
@check_index_permissions@ は管理者以外のすべてのユーザ（匿名・ログイン済みの
どちらも）に対して、グループ未設定のインデックスを不可と判定する。

v2.0.4 の @check_roles@ は @is_can = True@ から始まる「既定は許可」で、
このようなゲートは無かった。v2.1.0 の書き換え
（@check_roles@ → @check_index_permission_by_role_and_group@）で入った。

h3. 影響

* 公開アイテムの公開ファイルが*匿名で取得できない*。GakuNin RDM への
  エクスポートは外部サービスが匿名で取りに来る仕組みなので機能しない。
* 上の「優先度の高いもの（認可まわり）」の
  @invenio-records-rest::test_default_permissions@（匿名の単一レコード GET が
  401）も、これと同じ原因である。

  見えない*（@check_groups@ は認証の有無にかかわらず False を返す）。

h3. 対処

@weko_index_tree.utils@ を直す。空の @index_group_list@ は「グループ制限なし」
であって「誰も許可しない」ではないので、そのときは @True@ を返すべき。
テスト側では直せないため、@ui-tests/test_import_to_gakunin_rdm_button.py@ の
@test_import_to_gakunin_rdm_button_enabled@ は xfail にしてある。

h2. 未着手の懸案

*マイグレーション @e0dd9fb514cf_add_constraints_to_mapping.py@ が既存データを考慮していない。*

v2.0.4 の @Mapping.create@ は存在チェックなしで @add()@ していたため、
マッピングを保存するたびに @item_type_mapping@ に行が増える。
v2.0.4 の @get_record@ が @order_by(desc(created)).first()@ で最新行を選んでいたのは、
その重複が前提だったからである（v2.1.0 ではこの @order_by@ が落ちている）。

一方 v2.1.0 のマイグレーションは、データを掃除せずに一意制約と外部キーを張る。

<pre><code class="python">
batch_op.create_unique_constraint('uq_item_type_mapping_item_type_id', ['item_type_id'])
batch_op.create_foreign_key('fk_item_type_mapping_item_type_id_item_type',
                            'item_type', ['item_type_id'], ['id'], ondelete="CASCADE")
</code></pre>

稼働中の DB に重複行があれば @create_unique_constraint@ が失敗し、
*alembic upgrade がアボートして v2.1.0 への移行が完了しない。*

実データでの確認用クエリ:

<pre><code class="sql">
-- 重複
SELECT item_type_id, count(*) FROM item_type_mapping
 WHERE item_type_id IS NOT NULL GROUP BY item_type_id HAVING count(*) > 1;

-- 孤児（FK を張れない行）
SELECT m.item_type_id FROM item_type_mapping m
  LEFT JOIN item_type t ON m.item_type_id = t.id
 WHERE m.item_type_id IS NOT NULL AND t.id IS NULL;
</code></pre>
