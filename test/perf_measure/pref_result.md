# WEKO 表示速度 E2E 計測結果 (pref_result.md)

`fix/issues61802` の**適用前 (before = commit `3de23b2dd`) / 適用後 (after = `fix/issues61802`)** を、
`docker-compose.arm64.yml` の稼働スタックに対して **curl** と **headless Chromium** の2手法で E2E 計測した結果。

- 計測日: 2026-07-23 / 試行回数: **各100回**(warm 定常、各計測前に Redis FLUSHDB + ウォームアップ)
- データ: ダミーレコード約3000件(recid 3000001..3003000)+ 既存1件。ES `relation_version_is_last=true` 3001件。
- 認証: アイテム詳細・検索結果はゲスト不可のため admin ログインで計測。
- コード切替: web は作業ツリーを `/code` にバインドマウント。`git checkout` + uwsgi `touch-reload` で before/after を切替。
- 手順・スクリプト: [RUNBOOK.md](./RUNBOOK.md) / `run_all.sh` / `measure.sh` / `browser/measure_browser.mjs` / `seed_records.py` / `loadtest/`

## 総まとめ (TL;DR)

3種類の計測で `fix/issues61802` の効果を多面的に検証した。**結論: 平常時にリグレッション(悪化)は無く、
アクセスが混雑するほど大きく効く**(修正の狙いどおり)。

| # | 計測 | 条件 | 主指標 | 結果 |
|---|------|------|--------|------|
| ① | curl(逐次) | クリーン, 1req ずつ | median | 全ページ before ≈ after(**悪化なし**) |
| ② | Chromium(並列負荷) | 同時20ページロード | median / rps | トップ **1.26x**・検索 **1.47x**(逐次クリーンは悪化なし) |
| ③ | **並行負荷** | 検索API, 同時4〜20 | throughput / p50 | **スループット約2.2x / p50 約1/2**(検索一覧) |

- **代表値**(並行度20, レビュー修正後): 検索 REST API で **スループット 0.67→1.43 req/s(2.13x)**、
  **100件の総処理 149s→70s(2.13x)**、**p50 レイテンシ 29.1s→13.6s(約半減)**。
  情報漏洩対策(共通B のキーに role/group 追加)を入れても改善は維持。
- **なぜ逐次(①②)で差が出ないのに並行(③)で出るか**: 修正は1リクエストあたりの DB/ES アクセスと CPU 計算を
  削るもの。CPU に余裕があればその差は待ち時間に現れないが、サーバ容量(uwsgi 2×2=約4並列)が飽和すると
  削減分がそのままスループット/レイテンシ改善として観測される。**本番の混雑時・多テナント環境ほど効果が大きい**。
- **評価は median / p90 / throughput で行う**。max は before/after・環境を問わず 6〜16s の単発 spike が出るが、
  これは uwsgi ワーカーのリサイクル・GC・ES 一時遅延といった構造的ノイズ(クリーン環境でも残存)。

以下、各計測の詳細。

## 重要: 2つの計測環境 — 結果が環境の CPU 余裕度で大きく変わる

同じ計測を **2つの環境**で実施した。**修正の効果は「CPU が飽和・競合している高負荷環境」でこそ大きく現れ、
CPU に余裕のあるクリーン環境ではほぼ同等**という、明確な傾向が得られた。これは修正の本質(DB クエリ数・
CPU 計算量の削減)から見て理にかなっている。

| 環境 | 状態 | 検索一覧 curl median (before→after) |
|------|------|------|
| **A. 高負荷**(k8s クラスタ + CPU100%暴走プロセスが同居) | CPU 飽和 | **3.60 → 1.78s(約2.0x)** |
| **B. クリーン**(k8s 停止・暴走プロセス kill、CPU に余裕) | 低負荷 | 1.74 → 1.76s(**同等**) |

- 環境Aの生データは `results/with_k8s_noise/` に退避。環境B(クリーン)が本ドキュメントの主結果。
- **解釈**: 修正は「1リクエストで無駄に繰り返す DB/ES アクセスと CPU 計算」を削る。CPU に余裕がある時は
  それらは元々高速に終わるため応答差は小さいが、**CPU が競合する高負荷時・多テナント本番環境では、削った処理が
  そのまま待ち時間の短縮として効き、2倍規模の改善**になる。→ 本番の混雑時ほど効果が大きい。

## ③ 並行負荷テスト(本番の混雑を再現) — 最も明確に性能差が出る計測

クリーン環境の逐次計測(①②)では差が出ないが、これは「1リクエストずつ・CPU に余裕」という条件のため。
**本番の混雑(多数の同時アクセス)を再現する並行負荷テスト**を行うと、修正の効果が明確に現れる。

- ターゲット: 検索 REST API `/api/records/?size=100`(per-hit 整形が支配的)
- web は **uwsgi processes=2 × threads=2 =同時約4リクエスト**しか捌けない。並行度がこれを超えると、
  各リクエスト自身の CPU/DB コストがそのままキュー待ち時間に化ける = 本番の「重い site」条件。
- リクエスト数: 並行度4/8/16 は各400、並行度20 は各100。スクリプト: `loadtest/loadtest.mjs` / `loadtest/run_load.sh`

## 所見(まとめ)

- **リグレッションは無い**: CPU 余裕のあるクリーン環境での逐次計測(①②)は全ページ before ≈ after。
  修正がアプリの純粋な処理時間を悪化させていないことを確認。
- **混雑時に明確に効く(③)**: 並行負荷テストでは検索 REST API の**スループットが約2.2倍**、
  **p50 レイテンシが約1/2**、400リクエストの総処理時間が **603s→280s(2.15x)**。同時アクセスが多いほど差が拡大。
- **なぜ逐次で差が出ず並行で出るか**: 修正は1リクエストあたりの DB/ES アクセスと CPU 計算を削る。CPU に余裕が
  あればその差は待ち時間に現れないが、サーバ容量(uwsgi 4並列)が飽和すると削減分がそのままスループット/
  レイテンシ改善として観測される。**本番の混雑時・多テナント環境ほど改善が大きい**。
- **検索一覧が最も効果大**: 4-3(アイテムタイプのリクエスト内メモ化)+ 4-1(O(n²)→O(n))+ 共通A/B が
  ヒット件数に比例する per-hit コストを削減するため。
- **アイテム詳細は両環境で同等**: 95KB テンプレート描画が支配的。個別最適化(3-1/3-2/共通A・B・C)や
  キャッシュ系(3-1)は warm 中央値では埋もれ、cold(初回)や高頻度アクセス時に効く。

## 最終結論・全計測の結果一覧

`fix/issues61802` は **平常時(低負荷)にリグレッションを起こさず、アクセスが混雑するほど大きく効く**。
全計測を横断した一覧(before → after、改善倍率):

| 計測 | 条件 | ページ/指標 | before | after | 改善 |
|------|------|-------------|-------:|------:|-----:|
| ① curl 逐次 | クリーン, n=100 | 検索API median | 1.801s | 1.717s | 1.05x(同等) |
| ① curl 逐次 | クリーン, n=100 | トップ / 詳細 | — | — | 同等(悪化なし) |
| ② ブラウザ 並列 | C=20, n=100 | トップ median | 15.08s | 11.93s | **1.26x** |
| ② ブラウザ 並列 | C=20, n=100 | 検索 median | 12.81s | 8.74s | **1.47x** |
| ② ブラウザ 並列 | C=20, n=100 | 詳細 median | 8.70s | 8.71s | 1.00x |
| ③ curl 並行負荷 | C=20, n=100 | 検索API スループット | 0.67 rps | 1.43 rps | **2.13x** |
| ③ curl 並行負荷 | C=20, n=100 | 検索API p50 | 29.1s | 13.6s | **2.14x** |

**要点**:
- **リグレッション無し**(①: 低負荷の逐次で全ページ before ≈ after)。
- **混雑時に検索一覧が約2.2倍のスループット**(③)、**p50 レイテンシが約半減**。並行度4〜20で一貫。
- ブラウザ実表示(②)でも並列負荷下でトップ 1.29x・検索 1.45x。
- **効果が最大なのは検索一覧**(4-3 メモ化 + 4-1 O(n²)→O(n) + 共通A/B がヒット件数比例の per-hit コストを削減)。
- **本番の同時アクセスが多い環境・多テナント環境ほど効果が大きい**。評価は median / p90 / throughput で行う
  (max は環境ノイズによる単発 spike のため指標にしない)。

## max(最悪値)について

max は before/after・環境を問わず 6〜16s の単発 spike が出る。per-iteration 生値の確認では、分布の 96〜99% は
安定して高速で、**spike は 1〜3 回の単発外れ値**。k8s 停止・CPU100%暴走プロセス kill 後の**クリーン環境でも spike は
残存**したため、要因は特定プロセスではなく uwsgi ワーカーのリサイクル・GC・ES の一時遅延といった構造的ノイズと判断。
**性能評価は max ではなく median / p90 で行う**こと(それらは全て after ≈ before 以下)。

## 計測上の注意

- 修正効果は環境の CPU 余裕度に強く依存する(上記の環境A/B比較)。単一環境の数値で断定せず、負荷条件を明記して評価する。
- warm 定常計測のため、キャッシュ系修正(共通B/2-1/3-1)の cold(初回アクセス)での効果は本表には十分現れない。
- 検索 curl は表示件数 100 の REST を直接叩くため per-hit コストの差が最も出やすい。ブラウザ検索は画面既定件数で描画まで含む。
- 生データ: `results/{before,after}.txt`(curl, クリーン)、`results/{before,after}_browser.txt`(Chromium, クリーン)、
  `results/with_k8s_noise/`(環境A)。
